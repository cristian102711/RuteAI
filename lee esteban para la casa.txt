### Mapa de servicios y puertos
  - web (Next.js, BFF + frontend) ....... http://localhost:3000
  - ai-service (FastAPI/Express, scoring)  http://localhost:3001
  - auth  (Express, valida tokens) ....... http://localhost:3002
  - core  (Express, dueño de los datos)    http://localhost:3003

### Prerrequisitos en el PC de la casa
  - Node 20+  y  pnpm 9+   (el repo usa pnpm@9.15.0)
  - Una base PostgreSQL LOCAL. La forma más simple es Docker:
        docker run --name ruteai-pg -e POSTGRES_PASSWORD=postgres \
          -e POSTGRES_USER=postgres -e POSTGRES_DB=ruteai \
          -p 5432:5432 -d postgres:16
    (Si no tienes Docker: instala "PostgreSQL 16" para Windows desde
     enterprisedb.com y crea una base llamada "ruteai". Da igual el método,
     lo único que necesitas es una cadena de conexión postgresql://...)

### Paso 1 — Instalar dependencias (en la raíz del repo)
        pnpm install
  Esto, por el "postinstall" de packages/database, ya corre `prisma generate`
  y el cliente Prisma queda con los campos nuevos (fechaEntregaLimite,
  entregadoEn, intentosEntrega, etc. + el modelo EventoPedido).

### VEREDICTO GENERAL
  CORE está BIEN encaminado y respeta el patrón BFF (web orquesta, core posee
  los datos), con capas limpias route -> service -> repository y multi-tenant
  por empresaId. Está desplegable en Vercel y conectado a Supabase vía Prisma.
  Tenía 3 puntos a resolver: (1) de dónde saca la identidad (empresaId/rol),
  (2) observabilidad/logs casi inexistente, (3) endpoints inconsistentes o
  muertos.
  >> ESTADO: en esta sesión se RESOLVIERON los 3 (ver detalle marcado
     [RESUELTO] abajo). Queda como mejora opcional validar el JWT localmente
     (hoy mitigado con caché).

### A. CUMPLIMIENTO DEL MODELO BFF
  BIEN:
   - El web (apps/web) actúa como BFF real: valida sesión Supabase, reenvía el
     Bearer token a core (lib/coreServiceClient.ts), y orquesta lo "externo"
     (geocoding, IA, Twilio). Core NO conoce esas integraciones: sólo datos.
   - Core deriva el empresaId del token (no lo confía del body) -> buen
     aislamiento multi-tenant.
   - Envelope de respuesta consistente: { success, data, error, total? }.
  A MEJORAR:
   - Hay "controllers" vacíos y muertos: orders.controller.ts es literalmente
     `export class OrdersController {}` (igual locations/routes controllers).
     La lógica vive en los route handlers. O los usas de verdad o los borras;
     hoy confunden.
   - No hay middleware de error global ni handler 404 (el ai-service sí tiene
     404). Cada handler repite try/catch.

### B. DESPLIEGUE EN VERCEL
  BIEN:
   - api/index.ts exporta el app Express; vercel.json reescribe /(.*) ->
     /api/index con maxDuration 30. `app.listen` está guardado por
     NODE_ENV!=="production", correcto para serverless.
  A MEJORAR / RIESGOS:
   - PRISMA EN SERVERLESS: en Vercel cada función es efímera. Debes usar el
     POOLER de Supabase (host *.pooler.supabase.com:6543 con ?pgbouncer=true)
     en DATABASE_URL, y la conexión directa (:5432) sólo en DIRECT_URL para
     migraciones. Si core usa la conexión directa en runtime, agotarás
     conexiones bajo carga. (El web ya documenta esto en su .env.example; core
     debería seguir el mismo patrón.)
   - El singleton global de PrismaClient ayuda sólo dentro de una instancia
     "tibia"; no evita el problema de pool -> por eso importa el pooler.
   - CORS abierto (app.use(cors())) — para prod conviene restringir al origin
     del web.

### C. SUPABASE + LOGS (observabilidad)
  ESTADO ACTUAL: CORE casi no loguea nada (sólo el health lista endpoints).
  Eso hace muy difícil "ver logs" y depurar en Vercel. Compáralo con
  auth-service, que sí emite logs estructurados en JSON (auth.login.success,
  etc.) visibles en Vercel -> Functions -> Logs. Core debería hacer lo mismo.
  RECOMENDADO:
   - Middleware de logging de requests: método, ruta, status, duración, y
     empresaId/usuarioId del token. Una línea JSON por request.
   - Activar logs de Prisma en no-producción:
         new PrismaClient({ log: ["query","warn","error"] })
     y en producción al menos ["warn","error"].
   - Loguear los errores 5xx con stack (hoy se devuelven al cliente pero no se
     registran).
   - Dónde se ven: Vercel -> proyecto core -> pestaña Logs/Functions. Para la
     DB: Supabase -> Logs -> Postgres / Query Performance.

### E. HALLAZGOS CONCRETOS (con severidad y estado)
  #1 [ALTA] [RESUELTO] Identidad desde el TOKEN, no desde la DB.
     ANTES: auth /me devolvía empresaId/rol del user_metadata de Supabase; si
     faltaba empresaId, core respondía 403 en /orders, /routes, /locations.
     AHORA: el middleware de core valida el token con auth-service y luego usa
     la tabla Usuario (por id Supabase, fallback por email) como FUENTE DE
     VERDAD para empresaId/rol/nombre. Si no hay fila (onboarding pendiente),
     cae a los valores del token. -> apps/core/src/middlewares/auth.middleware.ts

  #2 [ALTA] [RESUELTO] Rol super_admin para empresas.
     El guard requireRole(["super_admin"]) es correcto (las pantallas /admin y
     /super-admin del web lo usan). El problema era que el rol no estaba
     declarado en el modelo. AHORA el comentario de Usuario.rol incluye
     "super_admin" y, como la identidad sale de la DB (#1), basta con poner
     rol="super_admin" a un usuario en la tabla Usuario para habilitar esas
     pantallas. CÓMO BOOTSTRAPEAR EL PRIMER SUPER_ADMIN: ver Parte 3, sección
     "Pendientes".

  #3 [MEDIA] [RESUELTO] Estados de Ruta inconsistentes.
     ANTES: schema decía "pendiente | activa | ..." y default "pendiente",
     pero la API usa "planificada | en_curso | completada | cancelada".
     AHORA: schema unificado (default "planificada", comentario corregido) y el
     repositorio crea la ruta con estado="planificada" explícito. El .sql
     incluye el ALTER del default para Supabase.

  #4 [MEDIA] [RESUELTO] Campo "velocidad" que no existía.
     AHORA el modelo Ubicacion tiene "velocidad Float?". El schema Zod y el
     repositorio ya lo pasaban; ahora persiste sin error. (Incluido en .sql.)

  #5 [MEDIA] [MITIGADO] Acoplamiento de red por request a auth-service.
     AHORA hay una caché en memoria por token (TTL 30s) en el middleware: se
     evita el fetch a auth/me y la consulta a la DB en requests repetidos.
     MEJORA OPCIONAL futura: validar el JWT de Supabase localmente (con el JWT
     secret/JWKS) para eliminar del todo la dependencia de red. Requiere añadir
     una librería (jose/jsonwebtoken), por eso se dejó como opcional.

  #6 [BAJA] [RESUELTO] Controllers muertos y health desactualizado.
     Se borraron orders/routes/locations.controller.ts (clases vacías). El
     health ahora lista todos los endpoints (incl. /:id/eventos y empresas).

  #7 [BAJA] [RESUELTO] Sin validación de entorno + sin manejo global de errores.
     index.ts ahora: valida DATABASE_URL al boot (falla rápido en prod), tiene
     logging de requests (JSON), CORS restringido por allowlist, handler 404 y
     manejador de errores global. prisma.ts activa logs de Prisma.
